OpenSpec：轻量规格层正在改变AI编程的游戏规则

当别人还在用” vibe coding “靠感觉写代码，OpenSpec 已经让 AI 在规格文档里”签字画押”再动手。

一句话理解 OpenSpec

OpenSpec 是一个轻量级的”规格驱动开发”（Spec-Driven Development）框架，由 Fission AI 团队打造，核心目标是：在写代码之前，先让 AI 把”要做什么”说清楚、写成文档，然后严格按文档执行。

它不是让 AI 直接写代码，而是给 AI 加了一层”规格合约”——代码动之前，规范先行。

为什么 AI 编程需要”规格层”？

先说一个大多数人都踩过的坑：

用 AI 编程助手写项目，写到一半发现 AI 输出的风格飘忽不定，同样的需求给出了完全不同的实现方式。而且一换对话上下文，AI 就把之前的约定忘得一干二净。

根本原因：AI 没有”记忆锚点”，没有持久化的规范约束。

Vibe Coding（靠感觉写）的问题：

  • 代码风格随机漂移

  • 实现与原始需求逐渐偏离

  • 项目规模扩大后”上下文腐烂”

Spec-Driven Development 的核心逻辑：在动手之前，先签一份”规格合同”——AI 和开发者都签字确认，双方按合同执行。这份合同是持久化的，不随对话结束而消失。

OpenSpec 怎么运作？

核心三步：提案 → 执行 → 归档

/opsx:propose  添加深色模式支持      ↓ 创建变更目录（包含 proposal.md、design.md、tasks.md）      ↓ /opsx:apply add-dark-mode   ← 执行实现      ↓ /opsx:archive add-dark-mode  ← 归档，规范合并入 specs/

目录结构

openspec/ ├── changes/          # 活跃变更 │   └── add-dark-mode/ │       ├── proposal.md   # 变更提案（what & why） │       ├── design.md     # 技术设计 │       ├── tasks.md      # 任务列表 │       └── specs/        # 规范增量（对原有规范的修改） ├── specs/            # 持久规范（被所有变更参照） └── archive/          # 已完成变更（历史存档）

关键设计：每个变更都是独立目录，所有相关文档（提案、设计、任务、规范增量）打包在一起，方便 AI 一次性理解全部上下文。

OpenSpec 的四个核心特点

1. 轻量——不需要 API Key，不需要 MCP

OpenSpec 本身只是规范管理层，不依赖任何 AI 供应商的 API。这意味着：

  • 不需要额外付费

  • 不被某个特定 AI 平台绑定

  • 可以搭配 Claude Code、Cursor、Codex、Windsurf、Gemini CLI 等 20+ 种工具使用

2. 迭代——不需要完整的瀑布式流程

OpenSpec 的哲学是 fluid、iterative、easy、built for brownfield。

没有 Spec-Kit 那样的七个阶段门控，也没有 Superpowers 那样的强制 TDD 技能触发。你随时可以创建提案、调整方向、重新执行。

这对于快速迭代的项目和已有代码库的渐进式改造特别友好。

3. 规范即文档——持久化的”规格合同”

/opsx:propose 创建的 proposal.md、design.md、tasks.md 不是一次性文件。执行完成后，这些文档会被归档并合并到 openspec/specs/ 目录，成为项目的持久规范。

这意味着：

  • 新对话中 AI 可以直接读取规范，理解项目的完整上下文

  • 规范不会因为对话结束而丢失

  • 团队成员可以看到”这个决定是怎么做出来的”

4. Brownfield 优先——为遗留项目而设计

OpenSpec 官方明确打出旗号：built for brownfield。

它的设计优先级是针对已有代码库的渐进式改造，而不是从零开始的白板项目。这意味着：

  • 可以局部引入规范，不影响现有代码结构

  • 规范层不影响 CI/CD 流程

  • 适合现有项目逐步迁移到规范驱动工作流

选型建议

选 OpenSpec 如果你：

  • 需要快速迭代，不喜欢严格门控

  • 在改造一个已有代码库（Brownfield）

  • 需要在多个 AI 编程工具间切换

  • 不想配置 API Key 和 MCP

选 Spec-Kit 如果你：

  • 在大型企业团队，要求流程可追溯

  • 希望通过规范直接生成代码

  • 需要阶段门控来控制质量

选 Superpowers 如果你：

  • 对代码质量要求严格，需要强制 TDD

  • 接受自动化触发的技能工作流

  • 只需要支持 Claude Code

实操：用 OpenSpec 驱动一个功能变更

场景：给项目添加”记住我”登录功能

Step 1：发起提案

在 AI 编码助手中输入：

/opsx:propose 为登录功能添加"记住我"选项

OpenSpec 会在 openspec/changes/ 下创建对应目录，内含：

  • proposal.md：功能描述和动机

  • design.md：技术实现方案

  • tasks.md：分解后的任务清单

  • specs/：对原有规范的增量修改

Step 2：AI 阅读规格，开始实现

新对话中，AI 可以通过 /opsx:read add-dark-mode 读取完整规格，理解需求背景和技术方案后开始实现。

Step 3：执行变更

/opsx:apply add-remember-me

Step 4：归档，规范沉淀

/opsx:archive add-remember-me

变更目录归档至 archive/，规范增量合并到 specs/，成为项目的持久组成部分。

为什么这个方向值得关注？

2026 年，AI 编程正在经历一个范式转移：

从”模型博弈”到”工程化落地”

早期的 vibe coding 靠感觉靠运气；现在开始需要结构、需要规范、需要持久化的”规格合同”。

三个驱动力：

  1. 上下文腐烂：项目规模扩大后，AI 需要持久化的规范来维持一致性

  2. 多工具协作：团队使用不同的 AI 编码工具，需要统一的规格层作为共享上下文

  3. 合规要求：企业项目需要可追溯的决策记录，规范层正好满足这个需求

OpenSpec 站在这个趋势上，定位清晰：轻量、通用、不绑定平台。它的核心价值不是替代 AI 写代码，而是让 AI 的行为有据可查、有规可循。
